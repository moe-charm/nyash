## 🚀 1. Phase 1のリスク - Hakorune VM完成

### 1.1 パフォーマンス劣化
**リスクレベル**: 🟡 Medium
**発生確率**: 80%
**影響度**: Medium

#### 問題
- Hakorune VMはインタープリタなので、Rust VMより遅い可能性
- 予想: 50-70%の速度劣化

#### 原因
- Hakoruneはインタープリタ言語
- Rustはコンパイル言語（ネイティブコード）
- オーバーヘッド:
  - Box型の動的ディスパッチ
  - GC頻度の増加
  - JSON parseのオーバーヘッド

#### 対策
1. **Phase 2 (AOT化) で解決**（推奨）
   - Hakorune VM全体をLLVMでコンパイル
   - 予想: Rust VMと同等以上（100-120%）

2. **ホットパス最適化**（補助）
   - ベンチマークで特定
   - クリティカルパスのみRust実装維持

3. **プロファイリング**
   - Rust VMとの比較
   - ボトルネック特定
   - 最適化ポイントの明確化

#### 受け入れ基準
- ✅ Phase 1完了時: 50%以内の劣化は許容
- ✅ Phase 2完了時: Rust VMと同等以上

#### リスク評価
- **Phase 1単独**: 🟡 Medium（許容範囲）
- **Phase 1+2**: 🟢 Low（解決済み）

### 1.3 レガシー命令のマッピング
**リスクレベル**: 🟢 Low

**影響度**: Low

## 🔧 4. Phase 4のリスク - Runtime置き換え

### 4.1 メモリ安全性の確保
**リスクレベル**: 🔴 High
**発生確率**: 70%
**影響度**: High

#### 問題
- Rustのメモリ安全性を失う
- セグメンテーションフォールト
- メモリリーク
- ダングリングポインタ

#### 原因
- Rustの所有権システムを失う
- GC実装のバグ
- FFI境界でのメモリ管理ミス

#### 対策
1. **GCは最小限のRust実装を維持**
   - GCアルゴリズム → Hakorune実装
   - Rust側 → 最小限のC ABIのみ提供（335行 → 200行）
   - パフォーマンス重視の部分は残す

2. **GC API設計**
   ```rust
   // Rust側（最小限のC ABI）
   #[no_mangle]
   pub extern "C" fn gc_alloc(size: usize) -> *mut u8 { /* ... */ }

   #[no_mangle]
   pub extern "C" fn gc_collect() { /* ... */ }

   #[no_mangle]
   pub extern "C" fn gc_mark(ptr: *mut u8) { /* ... */ }
   ```

3. **メモリリークテスト強化**
   - Valgrind/ASan対応
   - メモリリーク検出ツール
   - 定期的なGC実行

4. **Fail-Fast文化の維持**
   - メモリエラーは即座に失敗
   - デバッグ情報の充実

#### 受け入れ基準
- ✅ Valgrind/ASanでメモリリークなし
- ✅ セグメンテーションフォールトなし
- ✅ 509テストすべてPASS

#### リスク評価
- **発生時の影響**: 🔴 High（致命的）
- **対策後**: 🟡 Medium（慎重な実装で軽減）
